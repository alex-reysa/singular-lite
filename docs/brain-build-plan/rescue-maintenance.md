# September 10 delivery rescue

The user-authorized maintenance transition supersedes the old native-only recovery
procedure. Old R4 source reviews, failed candidate reviews, accounting and retained
worktrees remain historical. They do not grant acceptance under the replacement
runtime. No source9/R3 procedure cycle is a prerequisite.

The first maintenance boundary repairs bounded reconnect handling, exact-tree
fixture isolation, role/configuration routing, host-owned evidence delivery and
candidate/dispatch lifecycle. Fresh independent code review and a pinned host
regression gate precede runtime adoption. Later product work runs natively.

Evidence delivery supplies required packet and host verification bytes together
with their identities before the provider starts. Optional retrieval uses byte
pages through a host capability socket. SQLite charges repeat delivery before
return, retaining usage across restart and manifest refresh. Source tamper,
undeclared references, escaped paths, wrong identities and insufficient budgets
fail closed. Built-in adapters without an OS-enforced read-only sandbox are
unsupported for this delivery interface. Custom runners are trusted host
infrastructure and must enforce the same sandbox; the broker is not isolation
from the host itself. The initial runtime uses only the Codex adapter.

The evaluation counts integrated deliverables, ready-to-dispatch wait, retries,
delivery bytes, provider-reported token fields, host-gate time, and operator
interventions. Missing counters are unknown. A passing fixture is not native
work or proof of universal reliability. The retained baseline has two integrated
tasks and 1,861,065 charged recovery-review bytes; no causal efficiency gain is
claimed from those facts.

Durable operational checkpoint and raw measurements live in
`.singular-state/rescue-20260910/`. The old runtime must remain unchanged.
